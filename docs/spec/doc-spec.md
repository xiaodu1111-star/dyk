# Personal OS · 文档书写规范

> 版本：v1.0 · 2026-10-01
> 定位：本文件是**文档体系的总纲**。所有 L1 需求文档、L2 任务卡都必须遵循这里的格式与纪律。
> 唯一目标：**让不同窗口并发开发时不会互相踩，且你只需要审一份短文档就能放行。**

---

## 0. 一句话原则

**文档不是写给人看的记录，是写给"下一个窗口"的接口。**
写不清楚 = 并发时必撞车。所以每条信息只允许有一个归属地，重复即是错误。

---

## 1. 三层文档体系

| 层 | 目录 | 粒度 | 谁写 | 谁读 | 可变性 |
|---|---|---|---|---|---|
| **L0 契约** | `docs/contracts/` | 全局唯一 | 我（首次确定后） | 所有窗口 | **冻结后只读** |
| **L1 需求** | `docs/req/` | 一个功能点一份 | 我 | **你审核** | 审核通过后冻结 |
| **L2 任务卡** | `docs/tasks/` | 一个窗口一份 | 我 | 对应窗口 | 开工后只读 |

```
你的需求
   ↓
我设计 → 产出 L1 需求文档
   ↓
你审核（改 / 过）
   ↓
我拆分 → 产出 L2 任务卡 + 更新 L0 契约
   ↓
多窗口按 L2 并发开发（只读 L0，不许改 L0）
   ↓
我整合 + 联调测试
   ↓
交付
```

**L1 与 L2 的边界（最容易搞混，必须记住）**

- L1 回答：**「这个功能做完是什么样」** —— 业务行为、字段含义、验收标准
- L2 回答：**「这个窗口该改哪些文件、不许碰哪些文件」** —— 纯工程指令，不含业务讨论

L1 里出现文件路径 = 越界；L2 里出现业务讨论 = 越界。

---

## 2. L0 契约层（`docs/contracts/`）

这是并发开发的地基。**所有窗口都读它，没有任何窗口改它。**

| 文件 | 内容 | 何时更新 |
|---|---|---|
| `data-model.md` | 全部表结构、字段类型、索引、枚举值 | 有新表/改表时，**由我集中改** |
| `api-contract.md` | 全部接口：路径、方法、入参、出参、错误码 | 有新接口时，**由我集中改** |
| `conventions.md` | 包名、命名规则、统一响应体、常量枚举 | 极少变 |

**纪律（硬性）**

1. 契约文件由我（主窗口/整合窗口）统一维护，**功能窗口只读**。
2. 功能窗口发现契约有问题 → **不许自己改**，在回复里报告，由我统一裁决后改契约并同步所有窗口。
3. 契约一旦被某个窗口用于开发，改动必须**追加变更记录**（见 §6）。

## 3. L1 需求文档规范（`docs/req/`）

### 3.1 命名

```
REQ-<域>-<功能>.md
```
域取小写英文，与包名一致：`work` / `learn` / `fit` / `finance` / `life` / `system` / `dashboard`

例：`REQ-work-sop.md`、`REQ-life-habit.md`、`REQ-finance-transaction.md`

### 3.2 强制结构（固定 7 节，不许增删）

```markdown
# REQ-<域>-<功能> · <中文功能名>

> 状态：草稿 | 待审 | 已批准 | 开发中 | 已交付
> 迭代：P1 · 负责人：待定 · 更新：YYYY-MM-DD

## 1. 目标（一句话）
这个功能解决什么问题。不超过 3 行。

## 2. 用户故事
- 作为「我」，我希望 <操作>，以便 <收益>
（3–6 条，覆盖主要场景即可）

## 3. 功能点清单
| 编号 | 功能点 | 优先级 | 说明 |
|---|---|---|---|
| F1 | 新增 SOP | P0 | ... |
| F2 | 步骤编辑 | P0 | ... |

优先级：P0 必须 / P1 应该 / P2 可以

## 4. 数据规则
- 涉及哪些表（只写表名，字段细节在 L0 `data-model.md`）
- 关键业务规则（如：同一天重复打卡覆盖不新增）
- 边界条件（空值 / 超长 / 并发）

## 5. 接口清单
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /api/work/sops | 列表 |
（只写签名，详细出入参在 L0 `api-contract.md`）

## 6. 验收标准 ★
- [ ] 可验证的动作 → 可观察的结果
- [ ] 例：新增一条 SOP 并保存，列表页立即出现且使用次数为 0
（**这节是审核重点，必须每条都能当场验收**）

## 7. 不做的事（Out of Scope）
- 明确本期不做的项
（防止开发时擅自扩范围）
```

### 3.3 篇幅纪律

- **单份 L1 控制在 100–200 行。** 超过 200 行说明功能点太大，必须拆成两份。
- 不写实现细节（不用哪个类、不走什么设计模式）。
- 不贴大段 SQL —— SQL 在 L0。
- 不写"可能以后要"的东西 —— 那是路线图的事。

## 4. L2 任务卡规范（`docs/tasks/`）

### 4.1 命名

```
TASK-<序号>-<窗口名>.md
```
例：`TASK-01-backend-sop.md`、`TASK-02-frontend-sop.md`

也可以按窗口维度合成一份：`TASK-window-A.md`。

### 4.2 强制结构

```markdown
# TASK-<序号> · <窗口职责>

> 关联需求：REQ-work-sop
> 窗口：后端 / 前端 / 联调
> 依赖：无 / TASK-01

## 1. 本窗口目标
一句话说明这个窗口做完什么。

## 2. 独占文件清单 ★
本窗口**只允许**创建或修改以下文件：
```
personal-os-server/src/main/java/com/xiaodu/personalos/work/**
personal-os-server/src/main/resources/db/migration/V3__work_task.sql
```

## 3. 禁止触碰清单 ★
以下文件由其他窗口或主窗口负责，**本窗口一律不许改**：
```
personal-os-server/src/main/resources/application.yml
personal-os-server/src/main/resources/db/migration/V1__*.sql
personal-os-web/src/router/routes.ts
```

## 4. 交付物
- [ ] 具体文件 + 具体内容

## 5. 完成标准
- [ ] `mvn -q compile` 通过（后端）
- [ ] `npm run build` 通过（前端）
- [ ] 按 L0 api-contract 的出入参对齐

## 6. 遇到阻塞怎么办
1. 不许改契约、不许改别人的文件
2. 在完成汇报里写明「阻塞点 + 建议方案」
3. 由主窗口统一处理
```

### 4.3 并发切分铁律

**按文件切分，不按功能切分。**

| 规则 | 说明 |
|---|---|
| R1 | 每个文件在任一时刻**只能有一个窗口**拥有 |
| R2 | 前端窗口独占 `views/` `api/` `components/` `stores/` `types/` 下自己的子目录 |
| R3 | 后端窗口独占自己域的整个 package |
| R4 | 共享文件（路由表、菜单、Flyway 版本号、全局配置）**串行处理**，放在收尾阶段由主窗口统一合并 |
| R5 | Flyway 迁移脚本**版本号由主窗口预分配**，窗口不许自行编号 |

**共享文件白名单**（这几类必须串行，其余都能并发）

```
personal-os-web/src/router/routes.ts          路由注册
personal-os-web/src/layouts/DefaultLayout.vue 侧边菜单
personal-os-server/.../db/migration/V*.sql    Flyway 版本号
personal-os-server/.../application*.yml       配置
personal-os-server/.../common/**              全局通用（响应体、异常、枚举）
```

## 5. 文档状态机

```
草稿 ──我产出──> 待审 ──你审──> 已批准 ──拆分──> 开发中 ──整合──> 已交付
                    │
                    └──你打回──> 草稿（修订后重新提交）
```

- 状态写在文档头部的 `> 状态：` 一行。
- **未到"已批准"不许开工。** 这是唯一的人工卡点。
- 状态变更由主窗口改，功能窗口不许改状态。

---

## 6. 契约变更规则

L0 契约被改动时，必须在文件末尾追加：

```markdown
## 变更记录
| 日期 | 变更内容 | 影响窗口 | 是否已完成同步 |
|---|---|---|---|
| 2026-10-01 | work_task 增加 actual_min 字段 | TASK-01 | 是 |
```

**变更发生后，所有依赖该契约的在跑窗口必须被告知，并确认已同步。**

## 7. 命名与格式速查

| 对象 | 规则 | 示例 |
|---|---|---|
| 需求文档 | `REQ-<域>-<功能>.md` | `REQ-work-sop.md` |
| 任务卡 | `TASK-<序号>-<窗口>.md` | `TASK-01-backend-sop.md` |
| 表名 | `<域前缀>_<名词>` 蛇形 | `work_sop_step` |
| 接口路径 | `/api/<域>/<资源复数>` 小写中划线 | `/api/work/sops` |
| Java 类 | 大驼峰 | `WorkSopController` |
| 前端文件 | 视图大驼峰，其余小驼峰 | `SopDetail.vue` / `useQuickLog.ts` |
| 日期 | `YYYY-MM-DD` | `2026-10-01` |

## 8. 我要遵守的纪律（自查清单）

产出任何 L1 / L2 之前，我自查：

- [ ] 每条业务规则只在一处出现，没有重复
- [ ] L1 里没有文件路径，L2 里没有业务讨论
- [ ] 验收标准每一条都能"当场操作 + 看到结果"
- [ ] 单份文档没超过篇幅上限
- [ ] 任务卡的独占/禁止清单加起来覆盖了本次全部改动文件，没有遗漏的"共享文件"
- [ ] 涉及新表新接口的，L0 契约已同步更新
- [ ] 「不做的事」写清楚了

---

## 9. 你的操作方式（最简）

1. 你提需求（一句话也行）
2. 我产出 `docs/req/REQ-xxx.md`，把状态标成 **待审**
3. **你只需要看两节**：`3. 功能点清单` 和 `6. 验收标准`
4. 你说「过」或「改第 X 条」，我改完再给
5. 过审后我自动拆分任务卡，你开对应数量的窗口，每个窗口喂一份 TASK 文件路径即可
6. 全部完成后我整合、测试、交付，并把结果回写文档状态
